Engine A — invoice_pilot.py
Load .env + tokens/vishal.json, build Gmail credentials, open the API client.
Query subject:(invoice OR rechnung OR facture) has:attachment — search-first, not a full scan.
Page messages oldest → newest, batches of 50, max 5 parallel get calls.
For each attachment: type-gate the filename, then check invoice tokens in subject/snippet/body before downloading.
Decode base64, write to ~/dev-shared/docs/invoices/, append the message id to .seen.json, sleep 6s.

Rate-limit defense — the centerpiece
Zero 429s across a 6,500-email backfilldefense in depth
01Batch 50 messages, sleep 6s between batches → ~5,000 units/min, under the 6,000 cap
02429 → honor Retry-After, else exponential backoff 1s→2s→4s… capped at 30s, max 5 retries, resume not restart
03Max 5 parallel get calls — well under the ~50 concurrent hidden limit
04.seen.json checkpoint every batch → crash-safe resume
05Search-first query (has:attachment + subject tokens) → ~20× fewer calls than scanning everything

Interview framing — what to say
OAuth 2.0, not app passwords — mailbox password never stored.
Invoice recognition is a deterministic heuristic — Gmail search + filename + body regex, not an LLM. Faster, cheaper, reproducible.
Rate-limit engineering: batched, throttled, exponential backoff with checkpoint-resume — backfills 6,500 emails with zero API errors.
Idempotent via .seen.json, plus dry-run — safe to re-run at any time.
Two engines on one OAuth base: a standalone script for the workflow phrasing, an MCP tool driven by my AI agent for the agent phrasing — covers both readings of the task.
Backfill-then-incremental: the weekly cron scans 90 days once, then 7 days after that — flat cost going forward.
